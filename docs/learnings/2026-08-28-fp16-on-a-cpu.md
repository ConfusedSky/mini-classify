## fp16 on a CPU: the GPU's dtype, carried to a host that has no fast kernels for it (2026-08-28)

model-browser's web demo will serve the query API from a small VM with no
GPU, so the question was how slow so400m's text tower is on CPU cores and
whether anything cheap makes it faster. The first measurement — the shipped
`serve_api.py` under `CUDA_VISIBLE_DEVICES=` — read 1.1 s per query, and the
rest of the session was spent finding out that the number was an artefact of
one keyword argument.

All figures: embed-cache-test (2165 models, the demo corpus at
`~/Documents/tests/test-models/miniatures/deduplicated`), Ryzen 9 7940HS,
torch's default 8 threads, 16 queries at `top=60`, pool softmax.
`eval/cpu_dtype.py` is the re-runnable form; the table is its `--report`.

| variant | median query | peak RSS | rankings vs fp32 |
|---|---|---|---|
| fp16 — what shipped | 1.140 s | **7.7 GB** | identical (Jaccard 1.00 on all 16, max Δscore 1e-04) |
| fp32 | **0.310 s** | 2.8 GB | — |
| int8 dynamic, text tower | 0.097 s | 7.0 GB | top-1 differs on 3/16; top-10 overlap 4–10; Jaccard 0.46–0.90 |
| text tower only, fp32 | 0.369 s | 2.8 GB | identical |

### The dtype was the device's, not the host's

`load_siglip` defaulted `torch_dtype=torch.float16` for every caller. That is
the 4060's dtype and the one every cache was embedded under, and on the GPU
it is right. On a CPU it is wrong twice:

- **PyTorch has no fast half-precision kernels on x86.** The text forward
  runs 3.7× slower in fp16 than fp32 on the same cores.
- **The checkpoint is fp32 on disk** (4.3 GB in the HF cache for ~1.1 B
  parameters). Asking for fp16 reads the fp32 tensors and converts them,
  holding both for a moment: `ru_maxrss` 7.7 GB at load against a 3.4 GB
  steady state. fp32 never rises above its 2.8 GB steady state, because
  nothing is converted.

The second is the one that matters for a host. An 8 GB VM would OOM the
shipped configuration **during startup**, before its first query, and
model-browser would render that as the `wedged` state — a server that is
warming and never finishes, which is exactly what it would look like from
outside. fp32 fits a 4 GB host with room for the Bun server.

And fp32 costs nothing in results: rankings, scores and `best_z` agree with
the fp16 CPU run to four decimals on every query. The fix is one conditional
in `load_siglip` — fp16 for a `cuda*` device, fp32 otherwise, an explicit
`torch_dtype` still winning — pinned by
`tests/test_embedder.py::test_load_siglip_picks_the_dtype_by_device`.

### Two "obvious" CPU optimisations, measured so nobody retries them

**int8 dynamic quantisation** of the text tower's Linear layers is another
3× on top of fp32, and it changes what a user sees. Score deltas run to
0.037 on text-query cosines that sit around 0.1, so the top-60 reshuffles
(`a giant spider` keeps its top-10 and only 46% of its top-60; `dragon`,
`treasure chest` and `stone wall ruins` change their top-1). `best_z` moves
by up to ±1, which crosses model-browser's weak-match line at `WEAK_Z = 2.0`
for queries near it. Peak memory also went *up*, to 7 GB — the un-quantised
tower appears to stay reachable through `quantize_dynamic`, not chased once
the quality result had ruled it out. At 0.3 s versus 0.1 s the speed is not
visible; the reshuffle is.

**Loading only the text tower** (`SiglipTextModel.from_pretrained`) changes
nothing: same latency, same 1.2 GB after load, same 2.8 GB after the first
query. `from_pretrained` memory-maps the safetensors file, and pages are
resident only once touched — the vision tower's are never touched by a text
query, so the full model already costs what the text tower costs. The OS
does what the optimisation was meant to do. Not worth a line.

### What this does to the demo's hosting

Before: "8 GB, and probably 2.5–4 s a query on cloud cores." After: 2.8 GB
peak and 0.55–0.6 s pinned to four laptop cores (`OMP_NUM_THREADS=4
taskset -c 0-3`), so a 4 GB host is a candidate and 8 GB is comfortable. The
number still unmeasured is a real shared cloud vCPU, which is slower per core
than a 7940HS at boost; an hour on the target instance is the test.

### The trap, stated once

A dtype default that is correct for the machine the code was written on is
invisible until the code runs somewhere else — every caller passed the
device and none passed a dtype, so the argument that mattered was the one
nobody was looking at. The eval harnesses that "load on cpu" for counts
rather than timings (`compose_bounds.py`) had been paying the 3.7× and the
7.7 GB all along without a number that would have shown it.
