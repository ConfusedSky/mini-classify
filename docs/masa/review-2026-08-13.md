# Review of 2026-08-06 → 2026-08-13

Review note, 2026-08-13. Covers the 85 commits of that week — the pose pipeline,
the arbiter and its Gemini backend, the instrumentation spike, the numpy STL
parser, and the two research notes in this directory.

Five reviewers worked in parallel: pipeline code, instrumentation and scripts,
`renderer_alternatives.md`, `LEARNINGS.md`/`OPEN_QUESTIONS.md`/`eval/README.md`,
and `actors_proposal.md` plus the `eval/` harnesses. Numeric claims were
**recomputed** from committed data or re-measured by re-running the harness,
not read. Behavioural claims were checked against source.

## Verdict

**The code is in better shape than the documents.** Almost every measured
*conclusion* survived checking — the parser swap, the welding verdict, the
topology finding, the accuracy tables, the stage-timing method. What failed was
the prose around them: numbers superseded by later commits and never swept,
correct ratios attached to wrong explanations, and a `ready to do` list holding
two items that had already shipped.

One finding changes a decision rather than a sentence: **`eval/parser_gate.py`
has no A/A control, and its noise floor is larger than the effect it measures**
(§4.1). Every margin-level conclusion drawn from it is unattributable. It is
also the harness both notes name as "the pattern to copy".

Three claims that load-bear for the actor design are refuted (§3.1).

## 1. Code defects

Ranked by consequence. `file:line` as of `0943f86`.

### 1.1 `cleanup.sh` destroyed unrecoverable non-render data — FIXED

`cleanup.sh:5` was `rm -rf ./my_renders2/* ./embed-cache2/*`. The name and
comment say renders; `embed-cache2/` also holds `pose-cache.json` (~1.7 s/model
to rebuild, and any `"source": "vlm"` entry cost a paid ~24 s arbiter call), the
`walk-*.json` scans of a USB-mounted 1758-file collection, and
`run-params.json`. Deleting the last one **breaks `run_categories.sh`**, which
passes no input path and dies at `classify_stls.py:697`. None of it is in git.

`classify_stls.py:959` goes out of its way to save the pose cache even on
interrupt — "interrupted cold passes keep their (expensive) pose resolutions" —
which `cleanup.sh` then discarded unconditionally.

Rewritten in `275d60b`: renders and `*.npy` by default, `--clear-caches` and
`--clear-non-vlm-poses` for the pose/walk caches, `--dry-run`, and
`run-params.json` never deleted. No `rm -rf /` class bug existed (no variables,
no command substitution), but the old `./` paths meant the *caller's* cwd; the
script now `cd`s to its own directory.

### 1.2 A geometry-only pass silently poisons every later run — FIXED

`classify_stls.py:805-806, 836, 862-866`; `pose.py:105-122`

Pose entries are keyed on `file_identity` + `POSE_CACHE_VERSION`, and `entry is
None` is the only miss test. But `--skip-embed` and `--no-up-ensemble` call
`resolve_up` with `score_upright=None` (`classify_stls.py:785`), writing
geometry-only poses stamped `source: "heuristic"` at the current version.

A single `--skip-embed` pass writes 601 such entries. Every later ordinary run
hits the cache for all of them, so **the SigLIP ensemble and the margin gate
never run and the arbiter is never asked** — the exact failure the ensemble
exists to fix, cited in `resolve_up`'s own docstring (`32mm_Gate_L` scores 0.43
on the wrong face and passes both confidence tests). Nothing prints;
`pose_source` reads `heuristic`, indistinguishable from a confident geometry
answer.

The information needed to detect it is already in the entry — `margin` is `None`
exactly for geometry-only resolutions (`classify_stls.py:864`) — and is never
consulted.

Fixed two ways. `pose.pose_is_sufficient` now consults exactly that signal: a
run with the ensemble available treats a `margin: None` non-VLM entry as a miss
and upgrades it in place (announced up front), a geometry-only run still gets
its cache hits, and a paid VLM answer is kept whichever gate escalated it. It
gates both the `process()` hit test and the prefetcher's `wanted` list — fixing
only the former would have sent upgraded files into `prefetch.get()`
unannounced and retired the prefetcher. Separately, `--skip-embed` no longer
disables the ensemble at all: its intent was only ever to skip the final
classification embed, so geometry-only entries now come solely from
`--no-up-ensemble`.

### 1.3 An unhandled exception discards every completed row — FIXED

`classify_stls.py:801-961` (try/finally) vs `963-968` (CSV write); `:848`

`rows` is written *after* the `try/finally`, which does not suppress. Any
exception mid-run loses all results while the pose cache and run-params are
still saved: the run looks partly successful and produces no CSV.

The per-file `RENDER_ERROR` guard covers `prefetch.get` (843-847) and the
classification render block (885-894), but **not `resolve_up` at 848**, which
runs 24 renders and their embeddings.

Proved reachable: a degenerate binary STL (coincident vertices, or NaNs) passes
`load_mesh` and `up_axis_scores`, then makes `render_up_candidate_grid` raise
`RuntimeError` from Filament on an empty AABB. One such file at position 900 of
1758 discards 899 completed rows. Same shape for CUDA OOM in `embed_images` or
`np.save` failing on a full disk (911-913, also unguarded).

Fixed. The per-file guard now extends over `resolve_up`, so the degenerate-STL
case costs one `RENDER_ERROR` row. The CSV write moved into the `finally`,
restructured as nested finallys so each artifact is attempted whatever fails
before it — pose cache first (its VLM answers bill per gemini call; rows and
run-params only cost time), then rows, then run-params — with the last failure
re-raising and earlier ones chained as `__context__`. A torn `np.save` unlinks
its partial `.npy` rather than leaving a false cache hit. `embed_images` stays
unguarded deliberately: OOM is persistent, and dying fast now keeps every
finished row.

### 1.4 `render_up_candidate_grid`'s "pixel-identical" claim is false

`classify_stls.py:212-225` (claim) vs `:60-67` and `LEARNINGS.md:122`

The optimisation rotates the *camera* by `R.T` instead of rotating the mesh, and
claims to be "verified pixel-identical against the rotate-the-mesh version". But
`make_renderer` enables indirect light, and `classify_stls.py:64-66` states in
its own comment that the built-in environment map "is world-fixed and does not
orbit with the camera". Ambient fill therefore lands on the mesh in its original
orientation in one version and its rotated orientation in the other.

Measured on `blocky_building.stl` and `bunny.stl`, 384 px, 4 azimuths:

| candidate | pixels differing >2/255 |
|---|---|
| `(0,0,1)` (identity — control) | **0.00 %** |
| the other five | **6.4 – 15.9 %** |

`enable_indirect_light(False)` collapses all candidates to ≤0.11 %, isolating
the cause. For scale, `renderer_alternatives.md` quotes a 0.004 % noise floor.

Ensemble picks did not move on three fixtures, but margins shifted up to 0.099
against a 0.45 gate. The real exposure is that this claim is the stated proof
for `actors_proposal.md:139`, which proposes moving the same trick onto
`render_views` — that would change every classification render **without
changing any embedding cache key**.

### 1.5 `front_view` is cached without the keys it depends on

`classify_stls.py:918-919, 925`; consumers `cluster_models.py:38`,
`test_categories.py:144`

`front_view` is an index into *this run's* view list, persisted in
`pose-cache.json`, whose key is path+mtime+size only. The embedding cache keys
on views, elevations, render size and model (`cache_key`, 522-532); the pose
cache does not. So embeddings are correctly recomputed while the front index is
not.

Re-run at `--views 4` after an 8-view run and a cached `front_view: 6` survives:
`cluster_models.py` reports "front render missing" for every model. At
`--views 8 --elevations 20` — still in range — it silently picks the wrong
render as the hero tile, with no warning. All 601 live entries carry a
`front_view`.

### 1.6 `--pose-vlm claude` races on one scratch file

`pose.py:432`, reached concurrently via `classify_stls.py:812-814, 856-859`

`defer_arbiter` is enabled for `claude` as well as `gemini`, so up to
`--arbiter-workers` (default 8) threads run `ask_vlm_up` at once. Gemini and
ollama serialise the sheet into a per-call `BytesIO`; the claude backend writes
one fixed `pose-sheet.png` in `cache_dir` and hands *the path* to a CLI
subprocess that opens it later.

Two escalations in the same window and model A receives B's orientation, cached
with `source: "vlm"`. Silent and non-deterministic. The per-stem `save_to` debug
sheet is unaffected, so the only symptom is a saved sheet that disagrees with
the answer.

### 1.7 Stem collisions overwrite debug artifacts — FIXED

`classify_stls.py:284-293, 850, 881-882`

Renders and pose sheets are namespaced by stem alone across a recursive walk.
`pose-cache.json` holds **11 duplicate stems** among 601 models
(`Outpost_Ladder`, `tail`, `Barbarian_2H_Axe (repaired)`, …). Those files
overwrite each other, `render_index` then returns one path for both so
`need_renders` is False for the survivor, and the sheets show the wrong model.
Debug artifacts only — but they are what poses get graded from.

Fixed in `a27f9ab`: `render_key()` appends 6 hex chars of the resolved path to
the stem, wired through the writer and both consumers (`cluster_models.py`,
`test_categories.py`). `migrate_renders.py` renames existing images whose stem
identifies exactly one file and deletes the shared-stem ones — which model's
pixels survived the overwrite is unknowable — so those re-render on the next
`--save-renders` run.

### 1.8 Lower confidence

* **`embed_cache_token` has no code version for heuristic poses**
  (`pose.py:137-146`). The token is literally `"auto"`, on the argument that a
  heuristic pose is a deterministic function of the file. It is deterministic
  given *this* `up_axis_scores`/`GEO_FLOOR_POWER`. A future tweak that moves an

  Not live today; the guard the ensemble and VLM paths have is missing here.

* **The prefetcher retires permanently on any divergence**
  (`classify_stls.py:336-351`) — correct for the current call site; a symlinked
  directory yielding the same file twice would retire it silently for the rest
  of the run.
* **Dead import** — `classify_stls.py:45` `from pose import detect_up_axis` is
  unused.

## 2. Instrumentation

**Stage timing is trustworthy.** The timer is genuinely exclusive under nesting,
3-deep same-name recursion, exceptions thrown mid-stage, background-thread
stages, and an abandoned generator. Main-thread totals never exceeded wall.
Percentages are % of wall, main-thread-exclusive, and do not double-count. The
98.9 % in the published table leaves ~1.1 % for eight further stages; that
residual reconstructs to ~0.8 % of stage time plus ~0.3 % startup — **the budget
closes to within ~0.1 %**. The tables are simply truncated to the top rows.

**Per-stage device utilisation is not usable below ~1 s.** Two compounding
defects:

* Samples are stamped at **drain** time, not measurement time
  (`instrument.py:167-182`). Lines queue in the pipe while the sampler waits for
  the GIL. Measured: a 3.4 s gap, then 34 samples in 35 ms all mislabelled;
  ~77 % of `text-embed`'s rows physically describe `model-load`. The same
  artifact is visible in the committed `instrument.json`.
* The NVIDIA sensor updates every **~0.55 s** while the sampler polls at 100 ms,
  so ~5 of 6 samples repeat one reading. The docstring's "individual samples are
  noisy; the per-stage means are not" (`instrument.py:14-15`) is wrong *in kind*
  — this is systematic lag, not zero-mean noise, and it does not average out.

Smoking gun: `pose-geometry`, 11 ms of pure numpy on the CPU, reports **88 %
NVIDIA**. `psutil.cpu_percent(interval=None)` (`:171-172`) is garbage in the
same bursts — 30 zeros alongside spikes of 5402 %, both averaged in by `mean()`.
This undercuts the LEARNINGS claim about NVIDIA utilisation during
`embed`/`cache-save`, which describes exactly that sub-second regime.

**Utilisation percentages are also unbaselined.** Both sources are device-wide,
not per-process. Idle floors here are ~5 % NVIDIA and ~11 % AMD, so Spike 1's
"AMD 26 %" is ~15 points of renderer over an 11-point floor. "Nothing was ever
saturated" survives; the numbers do not.

**`mesh-wait` at 18.6 % is an upper bound**, for two independent reasons. First,
`prefetch.get()` falls back to a *synchronous* `load_mesh` when the prefetcher is
disabled, retired, or diverging — same stage name, measured at 45 ms/call with
prefetch on and 385 ms/call at `--prefetch 0`. Second, the 602-model run predates
`0943f86`, when `get()` loaded and discarded the meshes of every pose-cached file
*inside* that stage; `0943f86`'s own message quantifies 276 meshes / 11.6 GB in a
single `get()`. Estimated up to ~90 s of the 394 s total. The stated diagnosis —
"one prefetch thread at depth 2 does not keep up" — misattributes a list-plumbing
bug to insufficient loader parallelism, and that is the premise for
`loader_worker_count`.

**`report()` can lose the entire report.** `instrument.py:238` and `:279` iterate
`_totals` without `_lock` while `:102-104` mutates it under the lock. Reproduced
3/3: `dictionary changed size during iteration`, no JSON written, no breakdown
printed. Low likelihood, but `classify_stls.py:956` does `shutdown(wait=False)`
and `report()` runs at `:972` — the cost when it fires is a 35-minute run
yielding one line of text.

**Correct:** the `d03e68e` sampler reaping holds across normal exit, uncaught
exception, SIGINT, SIGTERM, SIGHUP and `os._exit` — no leak in any of them. And
**"across both GPUs" is supported**: the AMD iGPU is read from
`/sys/class/drm/card*/device/gpu_busy_percent`, not from nvidia-smi. The
docstring, the `--instrument` help text and `f9ec855`'s commit body all describe
this accurately; only the commit subject is loose shorthand.

Minor: the sampler passes no `-i`, so a second NVIDIA GPU would double the
sample rate and average across cards (`:155-158`); `% wall` is printed for the
async table where it can exceed 100 % (`:240-250`); `startup` and `other` are two
names for one bucket (`:41` vs `:101`).

## 4. Harness validity

### 4.1 `parser_gate.py` — margins not trustworthy — FIXED

What it gets right: it changes exactly one variable between arms, holds
renderer/model/prompts/size constant, seeds geometry sampling, and does report
`MARGIN_THRESHOLD` crossings separately (`:108-121`). Every quoted number
reproduces exactly from `eval/out/parser_gate_{384,2048}.json`.

**But reproducible is not attributable.** Arm A always renders before arm B
through one shared `OffscreenRenderer`, order never swapped, and
`LEARNINGS.md:505-524` already documents that prior scene state perturbs pixels.
The A/A control the harness lacks, run over five models:

| | mean margin shift | max |
|---|---|---|
| **A/A — zero variables changed** | **0.0169** | **0.0411** |
| A/B — loader changed | 0.0095 | 0.0203 |

On 3 of 5 models the A/A noise exceeded the parser's own effect. A second
reviewer independently measured A/A 0.0346 vs A/B 0.0219 — same direction.

Contaminated: the "0.024 mean margin shift" that "walked them across the 0.45
gate"; the `43→44` at 2048 on `Container_complete` (margins 0.00103→0.00171,
~6× below the documented state-noise floor); and every escalation crossing
including the tile9 finding in §3.2. **Surviving: "45/49 either way, 0/49 picks
moved" at 384 px** — a null result on picks is still meaningful.

Fixed: the harness now runs an A/A null control beside A/B with arm order
alternated per model, calls the production `resolve_up` instead of
reimplementing it, and counts missing meshes loudly (the six reorg orphans
were re-pathed and all 49 labels score). Over the full set the parser moves
0/49 picks and causes 0 crossings while the A/A control causes 2; margin-level
claims stay weak by construction at this renderer, which the harness now
prints as its verdict. LEARNINGS 2026-08-13.

Two more: `resolve()` (`:44-53`) **reimplements** `resolve_up`'s ensemble rather
than calling it, so "runs the production pose path" is an overstatement and the
gate will drift. And **6 of 49 labelled meshes are missing on disk** — the
collection was reorganised, `A Light In the Shadow/` now holds `All_32mm`/
`All_Busts` — and `except Exception: … continue` swallows `FileNotFoundError`
as a parse failure, so a re-run today silently scores 43 while `:67` still prints
"49 labelled models". As the named pattern to copy, this is the first thing to
fix.

### 4.2 `load_path.py` — partly trustworthy

Honest where the doc claims: it warms the page cache (`:59`) before any timer and
interleaves parsers, reporting the warm pass. The pixel-diff design is sound —
the control renders *last* while numpy soup renders second, so the noise floor is
measured at a larger state-distance than the comparison.

Two defects:

* **It does not measure the shipped parser.** `numpy_read` (`:45-55`) uses
  `np.frombuffer(fh.read(n*50))`, materialising the whole record block —
  precisely what production `read_binary_stl` avoids with `np.fromfile`. It also
  lacks the size guard and the ASCII fallback. Contaminates "numpy binary-STL
  120 ms" and the "419 ms / 9.9×" whole-path row.
* **Upload timing excludes the deferred portion** (`:96`) — no render before the
  timer stops, while Q1 says ~93 ms defers to the first draw. Contaminates
  "upload 275 ms" and the "6.6 % of the path" figure. The qualitative conclusion
  (parse dominates) survives; 6.6 % does not.

It also charges `compute_vertex_normals()` to the numpy arm inside the timer but
not to Open3D — conservative, so the real gap is *wider* than measured.

### 4.3 `renderer_open3d.py` — Q2 is not a controlled comparison

Geometry `"a"` is added at `:79` with the 3-arg form
(`add_downsampled_copy_for_fast_rendering=True`, the default); `"b"` at `:83`
with the 4-arg form (`False`). Q2 then compares `show_geometry("a")` against
`remove_geometry("b") + add_geometry("b", …, False)` — two variables. Production
`_upload` uses the 3-arg form, so the re-add arm matches neither. Contaminates
"34 ms / 369 ms / ~11×" in both documents. Direction favours a larger true ratio,
so the conclusion likely survives.

The ~11× is also strongly mesh-size dependent — it collapses to **1.4× at 57k
triangles**, so the collection-wide payoff is unmeasured.

### 4.4 `renderer_gil.py` — defensible; its use is not

The harness's spinner is a legitimate *relative* probe for C-extension calls, but
the arithmetic gives a lower bound rather than an occupancy: `BASE` is taken with
one runnable thread, so work occupying the GIL 100 % scores ~50 %. Its internal
inconsistency reproduces — `render_to_image` alone measures *longer* than the
combined line containing it — confirming the note's warning that only the
combined row is trustworthy.

`actors_proposal.md:404-413` nonetheless quotes the *isolated* figure, producing
**1.25 s of GIL per model against the renderer note's ~0.9 s** for the same
quantity — a ~39 % overstatement.

## 5. What held up

Worth stating plainly, because it is most of the week's work.

**The numpy STL parser** was checked hard and is correct: header/size arithmetic,
`<u4`/`<f4` endianness, the 50-byte record layout, `np.fromfile` continuing from
offset 84 after a buffered header read, and a non-probabilistic ASCII rejection
(bytes 80:84 of an ASCII STL imply an 8.5 GB file). Geometry is byte-identical to
Open3D's triangle soup on all fixtures; pose scores match to 5 decimals, so the
swap did not invalidate the existing cache. Malformed files return `None` and
fall through to the deliberate `ValueError` — working as intended, not a bug.

**`MeshPrefetcher` and the `0943f86` prefetch predicate** match their
documentation exactly — in-order delivery, exceptions re-raised in the consumer
with the prefetcher staying live, divergence retiring it, `--prefetch 0`
disabling cleanly, and `wanted` matching the single `get()` call site with no
stall and no waste.

**The deferred-arbiter hardening** (`f713ddf`, `2582d33`) is correct on every
path checked: pose resolved once per file, arbiter asked once, `pending_box`
always drained, `arbiter_pool` initialised before the `try`, per-future
exception isolation.

**The accuracy work reproduces cell for cell** — the @256/@512 table, the
newer-Gemini table, holdout columns, answer distributions, rescue and break sets,
the backbone sweep, front-first, the gauntlet block, `geo_floor` including the
subtle raw-vs-normalised escalation difference, sheet-fill, and the v3 arbiter
table. Ground truth is 49 labels, 23/21/5.

**In `renderer_alternatives.md`**, re-measured against the note: parse speedup

the pixel-diff figures near-exact (0.664 vs 0.665, 4.468 % vs 4.477 %). Absolute
wall-clocks ran ~1.7-2× slower than recorded — the machine was not idle — but
every ratio reproduced or improved. The EGL device mapping was verified
independently via ctypes (index 0 → NVIDIA, 3 → llvmpipe), as was the absence of
`eglQueryDevicesEXT` in Filament's binary.

Tests: **28 passed, 1 skipped** (ollama-gated). No coverage exists for
